QuickBite: Full-Stack Food Delivery Order Processing System
Revised assignment | FastAPI + RabbitMQ + PostgreSQL + Flutter
Version 2.0 | 12 October 2026
1. Assignment purpose and scope
Build a small, complete food-ordering application that runs in a browser, on Android, and on iOS using one Flutter project. Implement its API and asynchronous processing in Python with FastAPI, RabbitMQ, and independent worker processes. Demonstrate correct behavior when components fail, messages repeat, and multiple workers run concurrently.
This is a learning system, not a commercial delivery platform. Payment, restaurant confirmation, driver assignment, and notification delivery are simulated. Real card processing, maps, GPS tracking, inventory, refunds, taxes, and app-store publication are outside the required scope.
Required baseline: customer login, restaurant/menu browsing, cart and checkout, asynchronous order processing, order history and tracking, persisted in-app notifications, and a read-only admin overview. All three Flutter targets must be supported and tested. Polling is sufficient for live-looking tracking; WebSockets are an extension.
The same domain flow and API contract must work on all three platforms. A separate Python backend is deployed as a service; it is not embedded in the Flutter application.
2. Learning outcomes
Design a shared Flutter UI and adapt it to phone and desktop screens.
Define and consume a versioned REST API, including validation, authentication, pagination, and errors.
Separate synchronous API work from asynchronous processing using topic exchanges and queues.
Implement bounded retries, quarantine, manual acknowledgements, and safe event publication.
Handle repeated and concurrent deliveries without repeated business effects.
Keep database changes and outgoing messages consistent through a transactional outbox.
Measure queue backlog, API latency, recovery, and worker throughput.
Package, test, document, and demonstrate a reproducible full-stack application.

Flutter communicates only with FastAPI. Broker and database credentials must never be bundled in clients. Workers are separately runnable Python processes; they can share a domain package and database for this assignment. This is a modular, event-driven training architecture, not a requirement for independently owned microservice databases.
The API returns after a database transaction; it never waits for payment, restaurant, delivery, or notification workers. RabbitMQ distributes work. PostgreSQL is the authoritative source for order state. Flutter reads state from the API rather than inferring success from elapsed time.
4. Required technology stack
Backend: a supported Python release, FastAPI, Pydantic, SQLAlchemy, Alembic, PostgreSQL, and aio-pika.
Frontend: stable Flutter and Dart with web, Android, and iOS targets; an HTTP client and a documented state-management approach of your choice.
Messaging: a supported RabbitMQ release with the management plugin; durable exchanges and queues, persistent messages, publisher confirms, and manual consumer acknowledgements.
Packaging: Docker and Docker Compose for the API, database, broker, workers, outbox dispatcher, retry scheduler, and built Flutter web app.
Tests: pytest for backend tests; flutter_test and integration_test for Flutter; a repeatable HTTP load-test script or load-testing tool.
Pin container image versions and dependency versions, commit lockfiles where applicable, and document the exact versions used. Do not rely on floating latest tags. Use PostgreSQL for the required concurrency and transaction demonstrations; SQLite may be used only for an early prototype.

6. Domain model and state machine
Required records: users, restaurants, menu_items, orders, order_items, order_status_history, simulated_payments, driver_assignments, notifications, processed_events, outbox_events, retry_jobs, and quarantine_records. Equivalent normalized names are acceptable.
Orders store customer ID, restaurant ID, address, currency, total, status, version, failure code, optional driver ID, and UTC timestamps. Order items preserve menu ID, item name, quantity, and the server-authoritative price at checkout. Histories are append-only and record each transition and order version.
Use integer minor units for API money fields, for example 1250 for INR 12.50 with currency INR. Compute totals server-side from menu data. Reject inactive items, mixed restaurants, zero/negative quantities, and invalid addresses. Set documented limits such as at most 20 distinct items and quantities from 1 to 20. Do not accept client-supplied authoritative prices, customer IDs, or totals.
PENDING -&gt; PAID -&gt; CONFIRMED -&gt; DRIVER_ASSIGNEDPENDING -&gt; PAYMENT_FAILEDPAID -&gt; FAILEDCONFIRMED -&gt; FAILED
PENDING may become PAYMENT_FAILED after a permanent payment failure or exhausted payment retries. PAID or CONFIRMED may become FAILED after an unrecoverable restaurant or delivery failure. DRIVER_ASSIGNED is successful completion for this assignment; physical delivery is not implemented. PAYMENT_FAILED and FAILED are terminal.
Transient failures leave the order at its last successful state. Notification failures never change order status. Apply transitions with a row lock or compare-and-set version check inside a transaction. No backward transitions are allowed. Simulated refunds after a post-payment failure are optional; show a clear failure rather than claiming a refund was issued.

Scope the idempotency key to the authenticated customer and store a canonical request hash under a unique constraint. Repeating the same key and same payload returns the same acceptance response and Location with no new order or event, even if processing has since advanced. The client then fetches current status. Broker downtime does not invalidate a committed order: the outbox waits for recovery. Explicitly document this distinction in readiness checks and in the UI; an accepted PENDING order may be waiting for messaging recovery.

The correction is order.#, not order.*. A topic star matches exactly one segment; a hash matches zero or more segments. order.* matches order.paid, but misses order.payment.failed and order.driver.assigned. Notifications must cover those events.
Required event types: order.created, order.paid, order.payment.failed, order.confirmed, order.driver.assigned, and order.failed. Unknown schema versions or malformed messages go to quarantine rather than being retried forever. A notification worker may acknowledge a valid future event type it intentionally ignores, with a structured log.
Every event has an immutable event_id, schema_version, event_type, order_id, order_version, occurred_at, correlation_id, causation_id, and data payload. Use event_id as the idempotency identifier; retain it across redelivery. Use AMQP message_id equal to event_id, JSON content type, and persistent delivery mode. Retry attempts belong to delivery metadata, not a new domain-event identity.
{  "event_id": "evt_created_abc123",  "schema_version": 1,  "event_type": "order.created",  "order_id": "order_abc123",  "order_version": 1,  "occurred_at": "2026-10-12T09:00:00Z",  "correlation_id": "req_checkout_123",  "causation_id": null,  "data": {"customer_id": "user_1", "restaurant_id": "rest_123"}}
Workers can load authoritative order details from the shared database. Do not copy secrets or unnecessary personal information into events. Child events set causation_id to the incoming event_id and retain correlation_id. Payment, confirmation, assignment, and failure payloads include their relevant IDs or stable failure codes.
Use quickbite.dead as a durable direct exchange and orders.dead-letter.queue as a durable queue bound with routing key failed. Quarantined envelopes retain the original event, source consumer/queue, attempts, failure code, and timestamps. They must be inspectable through RabbitMQ management tools.
10. Transactional outbox and idempotent workers
An outbox record stores the exact outgoing event, destination exchange/routing key, available_at, delivery state, and a unique publication identity. Domain changes and outgoing event records commit in the same PostgreSQL transaction.
The dispatcher claims eligible records using a lock or lease safe for multiple dispatcher instances, publishes with publisher confirms and mandatory routing, and marks them sent only after confirmation without an unroutable return. A confirm alone does not prove a binding existed. Publication failures leave records eligible for a delayed retry.
A crash after publication but before marking the outbox sent can publish a duplicate. Therefore downstream consumers must be idempotent. Do not claim exactly-once message delivery. The requirement is at-least-once delivery with single committed simulated business effects.
Consumer processing sequence:
Validate the envelope and acquire the appropriate database lock.
Check a unique processed_events key of (consumer_name, event_id), where consumer_name denotes the logical worker type, not a process instance.
Check the current order state/version. Apply an allowed transition once; insert associated payment/assignment/history/notification records and outgoing events in the same transaction.
Commit the transaction, then acknowledge the incoming RabbitMQ message.
If the event was already processed, acknowledge it without repeating effects. If the transaction failed, do not record it as successfully processed.
Enforce database uniqueness for payment per order, driver assignment per order, notification per customer/event, and history transition/version. Mark successfully handled no-op stale events as processed where appropriate. Unexpected future-state prerequisites require a bounded deferred retry or quarantine, not a silent lost transition. Multiple consumers and retries can reorder events; use order_version for history/notification display and never regress state.
Payment simulation uses an order-based idempotency identifier. Real external payments would require the provider's idempotency mechanism and reconciliation; a local processed-event row alone cannot guarantee a real external charge occurs only once.
11. Bounded retries and safe quarantine
Required default policy: one initial attempt plus three delayed retries, approximately 2, 10, and 30 seconds, then quarantine. Permanent business declines and malformed messages may skip retries. Make attempts and delays configurable and record the effective policy in the README.
Baseline implementation: on a transient processing failure, roll back the business transaction, then atomically persist a retry_jobs record and a scheduled targeted outbox publication before acknowledging the original message. If the retry transaction fails, leave the original unacknowledged and reconnect/back off; do not acknowledge away the only surviving copy. Uniquely identify each consumer/event/attempt so repeated failure handling cannot schedule duplicate retry jobs for that attempt.
The scheduler makes due retries eligible for publication. Route retries only to the failing consumer's queue, for example through the default exchange with routing key payment.queue. Republishing a retry to the domain exchange would send it to unrelated subscribers again. Preserve the event_id and increment a durable attempt counter; successful processed-event checks still prevent duplicate effects.
When attempts are exhausted, transactionally persist a quarantine record and an outbox publication to quickbite.dead. For payment, also transition to PAYMENT_FAILED and emit order.payment.failed. For restaurant/delivery, transition to FAILED and emit order.failed. Notification quarantine preserves the order's business status and records notification failure. A malformed event without a valid order reference is quarantined without mutating an unrelated order. Acknowledge the source only after this database transaction commits.
TTL retry queues with dead-letter routing are an acceptable alternative if delays, per-consumer routing, counters, and safety are tested. Default dead-letter forwarding is not automatically lossless during broker/target outages. If relying on broker dead-lettering for the required guarantee, configure and document quorum queues with supported at-least-once dead-lettering, or use a confirmed application/outbox transfer. Do not treat durability or requeue=true as a complete retry policy.
Manual acknowledgements, finite prefetch, reconnect backoff, and graceful shutdown are mandatory. Do not use an immediate nack/requeue loop for known processing failures. A worker must stop accepting new work on shutdown and finish or safely abandon in-flight deliveries. The single-node Compose broker must use a persistent volume; recovery tests cover process/container restart, not permanent disk loss or full cluster high availability.
